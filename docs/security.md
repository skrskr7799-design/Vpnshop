## Конфигурация и секреты

**Текущее состояние.** `.env.example` и Compose рассчитаны на локальную разработку. Общая схема требует DB, cookie/JWT и параметры панели для всего процесса, проверяет минимальную длину ключей и пару OAuth ID/secret, SMTP обязателен при `NODE_ENV=production`. Публичный Fastify сейчас с `trustProxy: true`, admin — с boolean и необязательным CIDR. В dev mail fallback выводит полный текст письма, включая одноразовые ссылки. Платёжные адаптеры и конфигурация production proxy пока не представлены. [Пример env](../.env.example) · [Проверка env](../apps/api/src/config/env.ts) · [Public app](../apps/api/src/app.ts) · [Admin app](../apps/api/src/modules/admin/admin-app.ts) · [Почта](../apps/api/src/modules/mail/mail.service.ts)

| Окружение | Хранилище и адреса | Допущенные интеграции |
|---|---|---|
| Development | Локальные origins и БД, случайные dev-only ключи в игнорируемом файле. Compose bind только loopback. Для проверки писем локальный приёмник или fixture без печати реальных ссылок. | Mocks или тестовые аккаунты. Учётные записи персонала одноразовые. |
| CI | Эфемерный PostgreSQL и synthetic credentials job. Сетевое окружение без маршрута к production. | Mock подписей, SMTP и внешних HTTP API, параллельные тесты получают разные БД. |
| Staging | Отдельный Compose project/VPS, production-режим HTTP и раздельные origins, volumes, DNS, ключи и DB roles. | Sandbox мерчанта, стендовая панель и тестовый бот. Очищенная копия данных или синтетические данные. Импорт чувствительных данных ограничен процедурой restore. |
| Production | Зафиксированный VPS, собственные origins, ключи, credentials и backup namespace. Роли и сетевые ACL по схеме. | Только проверенные версии/мерчанты/группы. Не утверждённые каналы и методы авторизации закрыты конфигурацией. [Сети](deployment.md#топология-и-сетевые-соединения) |

Разделить `NODE_ENV` (режим runtime) и метку окружения (dev/staging/production). Типизированный startup preflight по роли проверяет scheme/host/порт и отсутствие query/credentials в обычных origins, staging/production HTTPS и разные web/admin host, фиксированные callback endpoints, точный issuer/namespace, безопасный объём пула, полноту интеграций и значения placeholder. Токены и ключи проверять на формат и версию без печати значения. Для production отказ при пустой ACL, конфликтующих origins, fail-open proxy, тестовом мерчанте, неизвестном panel instance или лишних секретах критичной роли. Неверный конфиг выбранного процесса блокирует его старт. Временная сетевая ошибка внешней службы переводит её в деградацию и проверяется в runtime. [Readiness](operations.md#liveness-readiness-и-признаки-деградации)

| Группа | Переменные и владелец | Доступ |
|---|---|---|

| PostgreSQL | Отдельный `DATABASE_URL` у public, admin, fulfillment, фоновых задач, migrator. Backup credential отдельно. | У runtime без прав владельца/DDL. Worker обновляет свою очередь и наблюдения, выдача права идёт через модуль Subscriptions, платежи — через Payments. Мигратор получает доступ только во время обслуживания. |
| Аккаунты и SMTP | `COOKIE_SECRET, JWT_SECRET`, отдельный ключ admin stage, версионированный ключ шифрования TOTP из области текущего `ADMIN_ENCRYPTION_KEY`, OAuth пары, `SMTP_URL`, Bot token при включённом Mini App. | Web credentials — public API, SMTP — отправитель, admin keys — admin API. Bot Management и Mini App различают bot token и OAuth secret. |
| Remnawave | `REMNAWAVE_URL, REMNAWAVE_TOKEN, REMNAWAVE_API_KEY, REMNAWAVE_INTERNAL_SQUAD_UUIDS`, разрешённые domain/subscription hosts и данные admit версии. | Worker — токен с правами назначения, public API — отдельный минимальный токен чтения профиля. Admin UI получает проекцию. Дополнительные proxy credentials только при поддержке у установки. Подстановку forwarding из приложения заменить доверенным прокси. [Транспорт](remnawave-integration.md#граница-адаптера-и-данные-postgresql) |
| Платежи | Проектные per-merchant credentials для create/read/refund, webhook verification key, allowed account/origin, список валют и режим sandbox/live. Имена конкретных переменных выбираются с адаптером. | Только процессу, который вызывает операцию. Аудит использует alias аккаунта. Верификация webhook отделена от права создавать возвраты. |
| Архив, TLS, уведомления | TLS private key, ACME DNS credential, archive upload, restore read, encryption key, credential alert sender. | Минимум доступов. Archive upload не предоставляет независимое аварийное чтение или удаление прошлых копий. Restore key и bootstrap доступа доступны после потери VPS. |

Начальный способ хранения — root-owned каталог вне checkout с файлами прав 0600 и защищённым родительским каталогом. Provisioning выдаёт файлу владельца UID нужного runtime в закрытом mount, остальные процессы не получают этот файл. Runtime читает свой read-only secret mount через адаптер `*_FILE` или утверждённый загрузчик. Поддержка `*_FILE` — требование к будущим entrypoints. Секреты не включаются в Compose YAML, build args, статические bundles, образы и их слои, Git и diagnostics. Маскирование env недостаточно при доступе к Docker daemon. Доступ к нему приравнивается к root. Релизный job с доверенного ref читает pull-only credentials и использует защищённый deploy environment. Хранение секрета проходит проверку в файлах, артефактах, истории образа, логах, core dumps и настройках frontend. Публикация manifest ограничивается именами ключей и digest.

## Данные, сессии и журналы

* Host-only HttpOnly/Secure cookies. SameSite=Lax для web/OIDC и Strict для admin. Для небезопасных cookie-запросов exact Origin, отдельные намерения OAuth/CSRF, admin reauth и обязательная server-side проверка прав. Refresh и access связаны с живым семейством, admin session проверяет expiry/idle и текущую роль. Origin админки не обслуживает публичные auth/reset.
* Пароль персонала выдаётся отдельной учётной записи через контролируемое приглашение. Первый ADMIN и восстановление последней доступной учётной записи требуют отдельной процедуры. TOTP и recovery codes проверяются и потребляются атомарно. TOTP secret хранится зашифрованным с версией ключа. Разрешения операции и субъект повторно проверяются при фиксации эффекта. [Административная аутентификация](identity.md#административная-аутентификация)
* Public, admin, edge и worker логируют по allowlist полей. В proxy path использовать шаблон без query, для callback/reset/subscription endpoints не журналировать чувствительные сегменты. Для Remnawave оставлять код категории, HTTP статус и длительность, исключить raw message; существующий клиент включает часть внешнего текста в ошибку. SMTP ошибка не содержит адрес и тело. Redact на уровне headers дополнительно исключает auth/cookie/set-cookie, X-Api-Key и подписи провайдеров. Проверять секреты-маркеры в логах всех уровней и при ошибках. [Логи](operations.md#журналы-и-идентификаторы) · [Клиент панели](../apps/api/src/modules/remnawave/remnawave.client.ts)
* Subscription URL передаётся только владельцу после свежей сверки. `Cache-Control: private, no-store`, запрет кэша edge, referrer и telemetry, QR локальный. Публичный Webhook принимает тело ограниченного размера для проверки подписи, сырые доказательства при необходимости доступны только авторизованному разбору по retention. Коды OAuth, token reset/verify, токены подписок, API secrets и реквизиты не входят в debug dumps, audit export или error reports. [Раскрытие ссылки](remnawave-integration.md#получение-конфигурации-владельцем)

## Границы доверия и угрозы

P0 блокирует коммерческий запуск. P1 должен быть выполнен до публичного пилота соответствующей функции. Проверки выполняются на изолированной среде и проверяют ожидаемый отказ, область доступа и отсутствие побочных записей. [Тестирование](testing.md)

| Приоритет и угроза | Компонент и мера | Проверка | Остаточный риск |
|---|---|---|---|
| P0 XSS | Web/admin: plain text для обращений, параметризация атрибутов, CSP из локальных scripts, без незарегистрированных источников, referrer и frame restrictions. | UI проверяет буквальное отображение тестовых строк, CSP и отсутствие исходящих обращений при QR. | Ошибка в зависимости или расширение браузера всё ещё может видеть открытую карточку. |
| P0 CSRF | Exact Origin, host-only cookies с подходящим SameSite, третья сторона только на OAuth callback с state/PKCE или webhook с подписью. Link через POST и proof. | Cross-origin изменяющее действие отклоняется, легитимный OAuth завершает привязку в той же family. | XSS на доверенном origin требует отдельной защиты. |
| P0 SSRF | Внешние URL выбирает сервер из конфигурации. Allowlist DNS/egress, TLS и запрет redirects для токенизированных запросов. Subscription URL не запрашивается сервером для проверки. | HTTP mock подтверждает отсутствие outbound вызова на неразрешённое назначение и отсутствие переноса заголовков при редиректе. | Компрометация DNS или доверенной интеграции требует контроля сети и TLS. |
| P0 SQL injection | Prisma с параметрами, tagged raw SQL для очереди, allowlist sort/filter. Runtime роли без DDL. | Code review запрещённых небезопасных raw вызовов, тест на валидацию фильтров и параметры запросов. | Ошибка сложного custom SQL или избыточный grant. |
| P0 IDOR/BOLA | Owner filter при чтении и изменении, проверка актуального состояния после HTTP, непрозрачный чужой/несуществующий ID. Admin — по permissions и DTO. | Два пользователя и два класса роли. Проверить объект, вложенный маршрут, пустую выдачу и side effects. | Поздно добавленная проекция или export без общего guard. |
| P0 Brute force | Лимиты IP, principal и mail recipient, окно отказов TOTP, журнал с безопасной причиной. Встроенный limiter одного процесса достаточен для локального burst, устойчивый счётчик по principal в БД для критичных стадий. | Тест синтетических серий, 429/lockout, нейтральный ответ recovery, reset счётчика по политике. | Злоумышленник может вызвать временный lockout, требуется процедура поддержки. |
| P0 Session hijacking | Проверка живой family и staff session, rotation/reuse detection, точный origin, отзыв при reset/logout/смене роли. | Проверить старый токен после ротации, logout и перехода роли, включая гонку refresh. | Уже раскрытая конфигурация требует собственного отзыва в панели. |
| P0 Privilege escalation | Support read-only по умолчанию. Для admin write — permission, step-up, причина, команда и audit в транзакции. Разделённые origins и креды сотрудников. | Матрица отрицательных сценариев backend, параллельное снятие админов и контекст CSRF. | Инсайдер с подтверждённым правом может принять неверное решение. |
| P0 Подделка webhook | Адаптер проверяет подпись по контракту и мерчанту/окружению, durable inbox, проверка суммы, валюты, финальности и reference, дедупликация подтверждённых событий. | Синтетические события с неверной подписью и контрольными расхождениями, replay после commit. | Подтверждённые интеграцией, но несопоставленные операции требуют сверки отчёта. |
| P0 Утечка subscription URL | Отдельное owner-only раскрытие, no-store на всех уровнях, QR локально, запрет передачи в audit и support, процедура ротации. | Проверка headers и markers в browser storage, proxy, traces и диагностике. | Скопированная ссылка может остаться на устройстве или в буфере. |
| P0 Небезопасный trust proxy | Закрытые upstream ports, proxy пересобирает заголовки, Fastify доверяет точному адресу/сети своего proxy. Admin ACL проверяет реальный peer с VPN. Не использовать безусловный `trustProxy: true`. | Контракт тестирует доверенный и недоверенный hop, доступ из разрешённого/запрещённого сегмента и влияние fake forwarding на req.ip/rate limit. | Ошибочная смена подсети Docker или внешнего LB требует повторного теста. |
| P0 Компрометация admin session | Серверный revoke, staff TOTP, одноразовые доказательства для write, отдельная приватная сеть, два администратора для согласованных операций. | Отзыв cookie до expiry и при активном подтверждении, отказ обычной сессии на admin origin. | Компрометация станции сотрудника во время подтверждения. |
| P0 Компрометация Remnawave token | Раздельные scopes и инсталляции, mTLS или ACL при наличии, запрет клиентского доступа, процедура остановки записей и ротации. | Стендовый токен чтения не может изменить пользователя, отзыв токена даёт отказ, свежий read-only probe успешен. | Внешняя панель может дать более широкие scopes. Ограничить сеть и принять остаточный риск перед запуском. |
| P1 Supply-chain | Lockfile и pinned images/actions по digest/SHA, allowlist install hooks, ограниченные CI rights, SBOM, отчёты зависимостей/образа, подписанный provenance. | Clean install, проверка подписи/идентичности перед deploy, scan на PR и релиз, закрытый runner без production credentials на недоверенных PR. | Новая уязвимость появляется после сборки. Регулярный повтор scan и план patch. |

## Ротация и компрометация

**Обычная смена.** Создать новый credential с минимальным scope. Развернуть его через versioned файл и перевести только нужный процесс. Если интеграция поддерживает overlap, проверить новый на стенде и коротком probe, затем отозвать старый по плану и проверить отказ. Для webhook overlap ограничен интервалом поставщика и набором известных key IDs. Обе подписи проходят одинаковые проверки и дедупликацию. При смене DB credential разделить роли/версии и обновить соединения bounded drain. Зафиксировать аудит без значений и дату следующего пересмотра.

| Секрет или инцидент | Немедленное действие | Безопасное возобновление |
|---|---|---|
| JWT/cookie/admin session/cred | Отозвать сессии, заблокировать затронутых сотрудников, аннулировать pending OAuth/stage/proof. При компрометации перестать принимать старый ключ сразу. | Новые ключи и повторный вход, TOTP по проверенной процедуре. Не оставлять бессрочный grace. |
| TOTP encryption | Остановить доступ затронутых учётных записей, отозвать стадии и сессии. Переиздание факторов и recovery по Identity. | При обычной ротации versioned decrypt/re-encrypt в проверенном окне. При утечке заменяются сами факторы. Старые backup keys хранятся отдельно до истечения retention. |
| Remnawave token | Остановить внешние записи и отозвать ключ в панели. Установить причину и диапазон изменений. | Новый ключ с ограниченным scope, контроль metadata и read-only сверка профилей. Спорные изменения в разбор, включение одного worker с verify-first. |
| Платёжные ключи | Приостановить новые затронутые create/refund, отозвать ключ. При риске подделки входящих подтверждений изолировать спорные события. | Сверить движения напрямую у провайдера с пересечением окна, проверить новый signing/merchant key и устойчивое соответствие reference. Не повторять неизвестную операцию на новом ключе автоматически. |
| Subscription URL | Удержать раскрытие по ситуации, подтвердить владельца и событие компрометации. | Применить санкционированную ротацию панели, подтвердить её чтением, сообщить владельцу о новом импорте через кабинет. |
| Backup/cloud/network credential | Отозвать скомпрометированные права, сохранить последний проверенный внешний архив, изолировать VPS при подозрении на доступ root. | Сменить секреты связанных ролей и проверить restore с новым доступом, проверить историю репозитория и approvals. |

При Critical сначала ограничить эффекты, затем собирать только разрешённые журналы и подтверждённые внешние факты. Согласовать ответственного и доступ к резервному управлению до запуска. [Инциденты](operations.md#реагирование-на-инциденты)
