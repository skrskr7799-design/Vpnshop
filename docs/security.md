## Конфигурация и секреты

**Текущее состояние.** `.env.example` и Compose рассчитаны на локальную разработку. Общая схема требует DB, cookie/JWT и параметры панели для всего процесса, проверяет минимальную длину ключей и пару OAuth ID/secret, SMTP обязателен при `NODE_ENV=production`. Начальный способ хранения — root-owned каталог вне checkout с файлами прав 0600 и защищённым родительским каталогом. Provisioning выдаёт файлу владельца UID нужного runtime в закрытом mount, остальные процессы не получают этот файл. Runtime читает свой read-only secret mount через адаптер `*_FILE` или утверждённый загрузчик. Поддержка `*_FILE` — требование к будущим entrypoints. Секреты не включаются в Compose YAML, build args, статические bundles, образы и их слои, Git и diagnostics. Маскирование env недостаточно при доступе к Docker daemon. Доступ к нему приравнивается к root. Релизный job с доверенного ref читает pull-only credentials и использует защищённый deploy environment. Хранение секрета проходит проверку в файлах, артефактах, истории образа, логах, core dumps и настройках frontend. Публикация manifest ограничивается именами ключей и digest.

## Данные, сессии и журналы

* Host-only HttpOnly/Secure cookies. SameSite=Lax для web/OIDC и Strict для admin. Для небезопасных cookie-запросов exact Origin, отдельные намерения OAuth/CSRF, admin reauth и обязательная server-side проверка прав. Refresh и access связаны с живым семейством, admin session проверяет expiry/idle и текущую роль. Origin админки не обслуживает публичные auth/reset.
* Пароль персонала выдаётся отдельной учётной записи через контролируемое приглашение. Первый ADMIN и восстановление последней доступной учётной записи требуют отдельной процедуры. TOTP и recovery codes проверяются и потребляются атомарно. TOTP secret хранится зашифрованным с версией ключа. Разрешения операции и субъект повторно проверяются при фиксации эффекта. [Административная аутентификация](identity.md#административная-аутентификация)
* Public, admin, edge и worker логируют по allowlist полей. В proxy path использовать шаблон без query, для callback/reset/subscription endpoints не журналировать чувствительные сегменты. Для Remnawave оставлять код категории, HTTP статус и длительность, исключить raw message; существующий клиент включает часть внешнего текста в ошибку. SMTP ошибка не содержит адрес и тело. Redact на уровне headers дополнительно исключает auth/cookie/set-cookie, X-Api-Key и подписи провайдеров. Проверять секреты-маркеры в логах всех уровней и при ошибках. [Логи](operations.md#журналы-и-идентификаторы) · [Клиент панели](../apps/api/src/modules/remnawave/remnawave.client.ts)
* Subscription URL передаётся только владельцу после свежей сверки. `Cache-Control: private, no-store`, запрет кэша edge, referrer и telemetry, QR локальный. Публичный Webhook принимает тело ограниченного размера для проверки подписи, сырые доказательства при необходимости доступны только авторизованному разбору по retention. Коды OAuth, token reset/verify, токены подписок, API secrets и реквизиты не входят в debug dumps, audit export или error reports. [Раскрытие ссылки](remnawave-integration.md#получение-конфигурации-владельцем)

## Ротация и компрометация

**Обычная смена.** Создать новый credential с минимальным scope. Развернуть его через versioned файл и перевести только нужный процесс. Если интеграция поддерживает overlap, проверить новый на стенде и коротком probe, затем отозвать старый по плану и проверить отказ. Для webhook overlap ограничен интервалом поставщика и набором известных key IDs. Обе подписи проходят одинаковые проверки и дедупликацию. При смене DB credential разделить роли/версии и обновить соединения bounded drain. Зафиксировать аудит без значений и дату следующего пересмотра.

| Секрет или инцидент | Немедленное действие | Безопасное возобновление |
|---|---|---|
| JWT/cookie/admin session/cred | Отозвать сессии, заблокировать затронутых сотрудников, аннулировать pending OAuth/stage/proof. При компрометации перестать принимать старый ключ сразу. | Новые ключи и повторный вход, TOTP по проверенной процедуре. Не оставлять бессрочный grace. |
| TOTP encryption | Остановить доступ затронутых учётных записей, отозвать стадии и сессии. Переиздание факторов и recovery по Identity. | При обычной ротации versioned decrypt/re-encrypt в проверенном окне. При утечке заменяются сами факторы. Старые backup keys хранятся отдельно до истечения retention. |
| Remnawave token | Остановить внешние записи и отозвать ключ в панели. Установить причину и диапазон изменений. | Новый ключ с ограниченным scope, контроль metadata и read-only сверка профилей. Спорные изменения в разбор, включение одного worker с verify-first. |
| Платёжные ключи | Приостановить новые затронутые create/refund, отозвать ключ. При риске подделки входящих подтверждений изолировать спорные события. | Сверить движения напрямую у провайдера с пересечением окна, проверить новый signing/merchant key и устойчивое соответствие reference. Не повторять неизвестную операцию на новом ключе автоматически. |
| Subscription URL | Удержать раскрытие по ситуации, подтвердить владельца и событие компрометации. | Применить санкционированную ротацию панели, подтвердить её чтением, сообщить владельцу о новом импорте через кабинет. |
| Backup/cloud/network credential | Отозвать скомпрометированные права, сохранить последний проверенный внешний архив, изолировать VPS при подозрении на доступ root. | Сменить секреты связанных ролей и проверить restore с новым доступом, проверить историю репозитория и approvals. |

При Critical сначала ограничить эффекты, затем собирать только разрешённые журналы и подтверждённые внешние факты. Согласовать ответственного и доступ к резервному управлению до запуска. [Инциденты](operations.md#реагирование-на-инциденты)

## Клиентский кабинет ACC-01–03

- Web access JWT проходит проверку живой family и действующей клиентской роли. Отзыв любого устройства, выход и reset вступают в силу в PostgreSQL. Refresh меняет токен под блокировкой владельца. При повторе вне 10-секундного окна сервер отзывает всё семейство.
- Публичный reset ограничен клиентами с подтверждённым email. Доставка нейтральна по статусу HTTP, лимит адреса сохраняется в PostgreSQL. Почтовые ссылки передают reset/verify token в fragment. Proxy и API должны исключать query OAuth callback, cookies, заголовки, тела, subscription URL и тексты поддержки из access logs и аналитики. Для Web API доверять только явно заданным `WEB_TRUSTED_PROXIES`. Ограничение IP через ненастроенный proxy может учитывать его адрес вместо адреса пользователя.
- C4 возвращает `private, no-store` и `no-referrer`. После HTTP повторяются проверки права и сессии, а QR рассчитывается локально. Серверный отзыв прекращает новую выдачу. Ссылку, уже скопированную в буфер или импортированную в VPN-клиент, браузер отозвать не может. Удержание доступа и ротация ссылки выполняются через отдельный эксплуатационный процесс.
- C8–C11 и A13 используют строгие schemas, BOLA-проверки и простые текстовые сообщения. Доступ к A13 проходит закрытый listener, Origin и staff permissions. Аудит содержит ID команды, автора и изменения статуса. Тексты переписки и причины поддержки не попадают в общий audit feed. Сообщения могут содержать сведения, самостоятельно введённые клиентом, поэтому срок хранения и доступ операторов должны быть закреплены перед релизом.

## ADM-01–03. Граница управления

Production требует отдельный HTTPS hostname и непустой ADMIN_ALLOWED_CIDRS. ADMIN_TRUSTED_PROXIES перечисляет точные адреса или ограниченные CIDR известных прокси. Сеть с нулевым префиксом отклоняется. Reverse proxy заменяет входящие forwarding headers перед передачей на закрытый listener.

Command proof одноразовый и связан с живой сессией, версией credential и HMAC нормализованной команды. После ожидания внутренних блокировок сервер повторяет проверку срока и откатывает эффект вместе с аудитом при ошибке. Секреты и ссылки исключены из результата. Код приглашения показывается после первичного commit, а результат повтора содержит только безопасные поля.

SUPPORT получает маскированные контакты, операционные данные заказа и чтение поддержки. Сводные деньги, финансовые операции, запись поддержки, staff и аудит требуют отдельных permissions. PostgreSQL защищает AuditLog от UPDATE/DELETE. Роль приложения получает SELECT/INSERT, а тестовый TRUNCATE доступен guard-проверенной одноразовой БД.

## Границы эксплуатации OPS

У каждого Node процесса свой DB URL. `mzt_migrator` владеет схемой. Роли `mzt_public`, `mzt_admin`, `mzt_worker`, `mzt_billing`, `mzt_notifications`, `mzt_backup` и `mzt_monitor` не владеют схемой. Public создаёт только PENDING Order и USER, admin не изменяет подтверждённый журнал, финансовый runtime закрыт до допуска адаптера. Monitor читает агрегирующий view и статусы миграций. Backup читает данные для восстановления, но не записывает финансовые факты. [Grants и RLS](../ops/db/grants.sql)

Из настроек Compose в secrets store передаются пути. Public получает ключ cookies/JWT и шифрования outbox. Admin получает ключ TOTP. Notifications получает ключ outbox и SMTP secret. Каждый TLS edge получает свой сертификат и ключ. S3 physical/logical получают разные credentials и ключи. Файлы не должны быть читаемы другими хостовыми службами. Репозиторий, образ и release manifest содержат только имена. Ротация DB: сменить пароль роли, заменить соответствующий URL, перезапустить потребителя, проверить readiness и отозвать предыдущую учётную запись. Ротация outbox: дренировать очередь прежним ключом или отдельно мигрировать ciphertext перед сменой. Утечка ключа TOTP требует отзыва административных сессий и переустановки факторов.

Admin требует отдельный HTTPS origin, положительный приватный ACL и известный proxy peer. Nginx пересобирает forwarded headers. Включение IPv6 требует эквивалентного firewall и сетевого теста на хосте. Любой прямой ingress к БД, metrics или runtime API запрещён. Допуск egress проверяется отдельно для SMTP, OAuth, provider, панели и S3. [Compose preflight](../ops/scripts/preflight.py)
