# VPNShop V2 · Authentication and Support

## Customer entry and recovery

- Email registration creates a pending request. When mail is configured, the Public API queues a 24-hour confirmation link. The response is neutral for unknown and existing addresses. The stored token is a digest, confirmation consumes it once, and concurrent confirmations for the same address serialize. Repeat a pending signup through the registration form.
- Without SMTP, the application records the signup request and tells the customer to contact the operator for manual activation. An authorized OWNER or ADMIN identifies the claimant and activates the request using the PASS 03 procedure. The operator delivers the temporary password via an approved private channel. The user must change it before receiving a full session.
- A provisioned or manually activated customer can later request confirmation at `/activation` or from Security. Manual activation leaves the address unverified. Email confirmation preserves the current password and account ID. Blocked accounts remain blocked.
- Automatic password recovery requires a confirmed address and available mail. The request response remains neutral. The one-hour recovery token is single-use and the transaction revokes existing sessions. New email links use URL fragments. The browser still accepts historical query links and clears token parameters before submitting.
- Google or Telegram enrolment and linking preserve existing orders, entitlements and financial history. A Telegram-only customer may add a real email from Security. Adding or verifying an address and setting a password are distinct operations with one-use proofs. Email addition must be completed in the browser that holds the initiating session. Replacing an already verified address is outside the current contract. Setting a password revokes all sessions. An external sign-in remains usable while its provider is configured.
- Security lists linked methods and active devices. Linking and removal require a fresh proof tied to the session and operation. Removal also needs another usable credential, checked transactionally while locking the user. Disablement by an operator retains existing bindings and can prevent access for customers who rely on that provider. Arrange an alternate credential before disabling it where possible.

## Operator configuration

Single/Core providers use the existing OAuth egress overlay and file-backed secrets. New templates default to disabled. Existing installations without explicit provider switches still follow the prior credential-and-egress configuration until the switches are set. Doctor reports rendered configuration and leaves live reachability unverified.

| Integration | Configuration | Callback on configured `PUBLIC_ORIGIN` |
| --- | --- | --- |
| Google | `GOOGLE_AUTH_ENABLED=true`, `MZT_ENABLE_OAUTH_EGRESS=1`, `GOOGLE_CLIENT_ID`, secret file `google_client_secret` | `/api/auth/oauth/google/callback` |
| Telegram | `TELEGRAM_AUTH_ENABLED=true`, `MZT_ENABLE_OAUTH_EGRESS=1`, `TELEGRAM_CLIENT_ID`, secret file `telegram_client_secret`, and `TELEGRAM_OIDC_VERIFIED=true` after approved contract testing | `/api/auth/oauth/telegram/callback` |
| SMTP | `MZT_ENABLE_SMTP_EGRESS=1`, `MAIL_FROM`, secret file `smtp_url` | The SMTP relay receives encrypted-outbox jobs from the existing notifications process |

Google uses a server-side authorization code exchange with PKCE S256, state, nonce, signed issuer/audience/authorized-party validation and verified email for new users. A matching local email requires interactive linking. Telegram uses the existing redirect adapter with a signed stable numeric Telegram identifier, PKCE S256, browser-bound state, and one-use callback consumption. Telegram nonce and provider freshness are deployment gates for the registered configuration. The adapter preserves its current non-nonce flow, and provider reauthentication requires a recent signed `auth_time`. When that proof is unavailable, an already-linked usable method is required. Keep Telegram disabled until its registered application proves login, claims, reauthentication and callback compatibility. Live Google, Telegram and relay delivery are external checks. [Google OIDC](https://developers.google.com/identity/openid-connect/openid-connect) · [Telegram Login](https://core.telegram.org/bots/telegram-login)

Only Single/Core application processes receive provider credentials. SMTP credentials are mounted only into the mail worker. On a host without SMTP the mail consumer profile is inactive, no mail work is added and the support inbox still receives internal events. A temporary SMTP error follows the bounded outbox retry schedule. Permanent recipient rejection terminates delivery for that job. Relay acceptance establishes transport acceptance. Delivery to the recipient inbox is a separate observation.

## Support

- Customers see their own cases, category, subject, status, linked order and conversation. Messages are plain text, at most 2,000 characters. Categories include subscription, payment, delivery, connectivity, technical issue, account, general and other. Older cases continue to display their original categories.
- **Waiting for support** is the initial `OPEN` state and the state after a customer reply. Staff may move an active case to **In progress**, **Waiting for customer**, **Resolved** or **Closed**. An ordinary staff reply asks the customer to respond. A resolved case can be reopened explicitly. Closing is terminal. Staff can still correct the internal priority or assignment on a closed case. The conversation remains available.
- SUPPORT reads cases and replies using the scoped `support:reply` command. ADMIN and OWNER use current command step-up for assignment, priority and status changes. The queue supports case, owner or order ID search, subject search and filters. Assignment requires an active credential and support-capable role. If the assignee is blocked or deactivated, the queue treats the case as unassigned while administrative history retains the former assignment.
- Each viewer has a read position. Opening the latest conversation reports the loaded snapshot position. A later write stays unread. Queue and inbox poll every 30 seconds while open. Support notifications are durable case events. Staff assignment and priority changes stay internal. Email is optional for public staff updates and includes a cabin link without the conversation.
- Customer creation, replies and status changes accept idempotency keys. Administrative changes use the existing command envelope, version, proof, idempotency and audit transaction. Customer writes and reads verify ownership, including read-mark and status endpoints.
