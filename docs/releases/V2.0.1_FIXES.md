# V2.0.1 — журнал исправлений по итогам VPS acceptance

Дата начала: 2026-11-27. Базовый релиз: v2.0.0, 594476766180425c08e7aeada6668bb4799207e2. Стенд Single: 1 vCPU, 1.9 GiB RAM, 2 GiB swap. Критерии VPS-приёмки остаются открыты до проверки на стенде.

## FIX-001 — P1 — ресурсные профили

Реализация: preflight читает CPU и RAM из Docker, проверяет каждый Compose-сервис. Профиль хранится в config/resources.env. Micro задаёт DB 1 CPU, 512 MiB, shared_buffers 64 MB и work_mem 2 MB. Нагрузочная ёмкость Micro требует измерения.
Docker отклоняет создание DB: `range of CPUs is from 0.01 to 1.00, as there are only 1 CPUs available`. Compose DB задаёт 1.5 CPU и 2g RAM. Временный обход: сохранён оригинал Compose вне релиза, локально DB CPU 1.0, RAM 512m; штатный up успешен, 13 сервисов running, status healthy, миграции применены. Локальный релиз модифицирован, не считать неизменённым аттестованным архивом. Приёмка: определение ресурсов Docker, профили и операторские overrides вне релиза, проверка всех сервисов до запуска, настройка PostgreSQL, измерение RAM/OOM под нагрузкой, CI для малых и больших хостов, сохранение настроек при обновлении. Micro 1 CPU/2 GiB — кандидат, не гарантированный минимум.

## FIX-002 — P1 — диагностика Docker

Реализация: CLI классифицирует известные отказы Docker по безопасным признакам, показывает этап и известный сервис. Необработанный stderr остаётся внутри процесса.
`vpnshop up` скрывает причину за exit code 1. Обход: прямой запуск `current/scripts/preflight.py --role single --release-env /opt/vpnshop/current/release.env -- up -d --wait db`. Приёмка: безопасный ограниченный вывод причины, этапа и сервиса; не раскрывать секреты, stdin, DSN или токены; тесты ошибок pull/create/start.

## FIX-003 — P1 — интерактивный OWNER bootstrap

Реализация: раздельные дескрипторы /dev/tty; скрытый ввод прекращается при недоступности termios. PTY покрывает диалог и отсутствие эха.
`vpnshop admin bootstrap` завершился общей ошибкой до приглашения ввода. Подозреваемый источник: `open('/dev/tty', 'r+', encoding='utf-8')` в local_admin; режим требует seekable stream. Обход подтверждён пользователем: скрытый ввод в shell, передача через `--username owner --password-stdin`; OWNER создан, admin list показывает аккаунт. Точный errno ещё не измерен. Приёмка: корректный раздельный ввод/вывод терминала, скрытый пароль и подтверждение, bootstrap/recover, PTY-тесты, noninteractive stdin/file, EOF и отсутствие TTY, отсутствие секретов в выводе.

## FIX-004 — P2 — история операций

Реализация: к существующей JSONL записи ошибки добавлены stage, service и безопасный код reason. Чтение предыдущих записей сохранено.
history.log содержит только ReleaseError для up и общую ошибку admin. Приёмка: безопасные структурированные stage/service/reason codes, без секретов; сохранение совместимости чтения истории.

## FIX-005 — P1 — UX создания клиента без временного пароля
Уточнение владельца: без SMTP не генерировать ссылки активации или временные пароли. OWNER вводит только email. Согласованный сценарий: клиент задаёт пароль в pending-заявке, администратор после независимой проверки заявителя подтверждает её; до подтверждения нет полноценной сессии, доступа к балансу, подпискам и данным. Не позволять знанию email само по себе давать доступ к аккаунту или закреплять чужой credential без возможности безопасной отмены заявки. Проверить гонки, захват pending-заявки, повторные попытки, существующие аккаунты, rate limit. Восстановление без SMTP через поддержку Telegram с ручной проверкой владельца. Компромисс согласован владельцем 2026-11-27.

## FIX-006 — P1 — ручное подтверждение регистрации
Для самостоятельно зарегистрировавшегося клиента убрать обязательную замену пароля администратором. Сохранить исходный credential и подтверждать только после независимой идентификации заявителя. Защититься от pre-account takeover: при сомнении в принадлежности исходного credential использовать защищённую активацию/новую установку пароля, не активировать чужую заявку. Ручное подтверждение не означает verified email; не снимать блокировку. Тесты авторизации, гонок и повторов.

## FIX-007 — P1 — риск-ориентированный step-up
Наблюдение: пароль запрашивается при подтверждении клиента и ответе на тикет. Убрать повторный ввод для обычных операций (ответы, подтверждение, создание клиента); классифицировать остальные команды по риску, включая публикацию цен и создание сотрудников. Сохранить свежий step-up для финансовых, привилегированных и security-операций; короткое окно доверия — предложение, требует threat model, привязки к сессии и отзыва. Не ослаблять RBAC, CSRF, idempotency, version checks, audit, проверку полномочий в транзакции. Согласовать матрицу API/UI, тестировать обходы.

## FIX-008 — P2 — причина только по делу
Убрать обязательную причину для ответа на тикет, подтверждения клиента, создания клиента и сотрудника. Сохранить автоматический аудит actor/action/target/time/result и безопасные изменения. Причину требовать для обоснованных операций (например, корректировка баланса, блокировка, возврат); пересмотреть контракт и UI совместно. Тесты обязательности по типу команды, отсутствие фиктивных причин.

## FIX-009 — P1 — управление паролем клиента из админки
Запрос владельца: ручная смена пароля и отправка ссылки сброса при SMTP, без временных паролей и лишних механизмов. Предложенная матрица: ориентироваться на текущие подключённые credentials, а не исходный способ регистрации. OWNER/ADMIN могут установить новый постоянный пароль для аккаунта с существующим password credential после проверки личности клиента и чувствительного step-up; SUPPORT не может. Не требовать причины или обязательной смены при следующем входе. Завершить старые сессии, инвалидировать outstanding reset proofs, сохранить автоматический аудит без пароля. Для аккаунтов только Telegram/Google не создавать пароль административным сбросом; использовать провайдера. При привязанном password credential и подтверждённом email + SMTP разрешить отправку ссылки через существующий recovery/outbox механизм, без нового генератора; не раскрывать токен оператору, rate limit, проверка полномочий. UI показывает подключённые способы входа и объясняет недоступные действия. Отдельное завершение всех сессий — проверить существующую возможность, не дублировать. Проверить смешанные credentials, отключённый SMTP, unverified email, OAuth-only, RBAC, отзыв сессий и аудит. Детали матрицы предложены ассистентом, окончательная реализация после review.
