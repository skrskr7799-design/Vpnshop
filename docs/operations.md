Phase 5. Проектные значения для начального VPS калибруются на стенде. Дежурный видит раздельно подтверждённые деньги, право на услугу, желаемое назначение и последнее наблюдение панели. [Развёртывание](deployment.md) · [Платежи](payments.md) · [Выдача](remnawave-integration.md)

## Выдача и фоновые процессы

Использовать очередь PostgreSQL из фаз 2–3. Текущие `lockedAt`, `targetExpireAt`, порядок захвата и requeue полезны как основа. Они не обеспечивают целевую защиту от commit старого worker. До конкурентного режима нужны общая аренда на подписку, monotonic token, проверка текущей revision и числа обновлённых строк на каждом переходе. Не смешивать legacy worker и worker с новой моделью на одной очереди. [Текущая очередь](../apps/api/src/modules/fulfillment/fulfillment.queue.ts) · [Протокол Phase 3](remnawave-integration.md#протокол-выдачи)

1. При старте проверить доступ к PostgreSQL и совместимость схемы, зафиксировать heartbeat со временем БД. Проверить метаданные и допустимые группы Remnawave прежде изменяющих вызовов. Сверку и паузу записей различать. Запоминать причину паузы и версию релиза.
2. Захватывать due задачи короткой транзакцией SKIP LOCKED с общей lease на подписку. Перед HTTP проверить revision, удержания, owner, token и запас lease на deadline. Начальный lease 90 с с HTTP deadline 20 с и watchdog. После непредвиденной задержки продлевать только действительный lease, устаревшие результаты локально отклонять. БД недоступна → прекратить новые захваты и внешние изменения, незаписанный результат считать неизвестным. После возврата БД перечитать задачу и панель.
3. При SIGTERM остановить приём задач и readiness, довести активную обработку до условного commit в пределах grace либо оставить intent с неизвестным исходом до истечения lease. У поддерживаемого graceful shutdown сохраняется маркер завершения drain. SIGKILL/потеря питания ведёт к тому же восстановлению. После рестарта expired lease проверяется по часам БД. Результат записи не восстанавливается из памяти.
4. Временные ошибки повторять из durable очереди с jitter. Начальный backoff 15 с с ростом до 30 мин, учитывать Retry-After. Ограничить число попыток и одновременно активных HTTP. Для 401/403 или несовместимой сборки приостановить записи на инсталляцию, оповестить и проверять контрольное чтение. После исчерпания бюджета отправить в NEEDS_REVIEW со стабильным кодом и историей. Операторский retry запускает сверку актуальной revision из админки с аудитом. Финансовый grant при этом не создаётся.
5. Независимая сверка читает также CONFIRMED и записи с hold. Первые в очереди — неизвестные записи, просроченные запреты и изменения на границе периода. Начальная цель — проверить неизвестное после восстановления связи, доступную панели блокировку в течение минуты, подтверждённые записи в пределах суток. Для платежей частота определяется каналом: как старт каждые 5 мин для due/UNKNOWN, ежедневный отчёт с перекрытием окна и устойчивым checkpoint. Уведомления идут через durable outbox, после commit и со своим бюджетом retry. [Параметры выдачи](remnawave-integration.md#ошибки-повторы-и-сверка) · [Сверка денег](payments.md#операционная-сверка-и-контрольные-равенства)

| Отказ | Восстановление и контроль |
|---|---|
| Воркер упал до вызова | Следующий захват после истечения lease берёт новую аренду и читает актуальную цель. Если уже есть intent с неизвестным исходом, начать с чтения панели. Дата берётся из сохранённого назначения. |
| Вызов успешен, процесс упал до commit или потерял ответ | Перевести попытку в VERIFY_PENDING. GET по проверенному ID и чтение управляемых полей. Совпадение подтверждается новой попыткой, расхождение ведёт к применению актуального абсолютного профиля или ручному разбору. |
| Два конкурирующих worker | Один валидный lease на подписку. Устаревший token не фиксирует результат. Для уже отправленного HTTP панель 3.4.9 не предоставляет CAS. Независимая сверка обнаруживает и исправляет допустимую позднюю запись. [Ограничение API](remnawave-integration.md#нехватка-гарантий-в-api-и-отдельное-предложение-upstream) |
| Пользователь продлил во время предыдущей задачи | Локальная транзакция публикует одну новую revision. Старое подтверждение условно отклоняется. Последняя цель учитывает все оплаченные интервалы, повтор старого заказа не начисляет срок. |
| Возврат изменил право | Применяется новая revision с текущими удержаниями и периодами. Локальная выдача ссылки закрывается с commit, если право прекратилось. Оператор контролирует время отключения на панели и сверяет поздний drift. |
| Remnawave недоступна | Кабинет показывает оплату и ожидание выдачи раздельно, ссылка при недоступном чтении закрыта. Backoff, ограниченный параллелизм, приоритет запретов после восстановления. Оплаты, периоды и задачи сохранены. |
| Ручная блокировка или пропажа пользователя | Зафиксировать наблюдение, прекратить раскрытие ссылки и запись профиля. Неизвестный DISABLED/MISSING передать оператору. Снимать конкретный hold или подтверждать новую привязку через команду с аудитом. [Правила Phase 3](remnawave-integration.md#ручная-блокировка-limited-и-удаление) |

## Liveness, readiness и признаки деградации

| Проверка | Условие |
|---|---|
| Public/admin liveness | Процесс и event loop отвечают на лёгкую probe, без DB и сети. Публичный `GET /api/health` возвращает только статус. Admin probe локальна или закрыта ingress. |
| Public/admin readiness | Конфигурация принята, listener не дренируется, DB доступна в пределах 1–2 с, схема входит в поддерживаемый диапазон и соединение под runtime ролью работает. Ошибка → 503. Proxy/release gate отслеживают готовность отдельно от restart, DB outage не вызывает бесконечный рестарт. Публичный `/api/ready` при экспонировании не содержит деталей зависимостей. |
| PostgreSQL | `pg_isready` проверяет процесс, SQL probe под минимальной ролью — read/write возможности по назначению, занятость соединений, место, архив WAL. Пробы приложения сверяют собственную готовность независимо. |
| Remnawave, оплаты, SMTP | Last successful probe, результат, latency, версия/merchant alias и safe reason. Ошибка панели затрагивает только операции, которым она нужна. Внешний провайдер при сбое помечает свой канал, durable inbox и факт подтверждённого платежа сохраняются. |
| Worker и расписания | Heartbeat каждые 15 с, возраст отметки, last completed tick, oldest ready, число due и занятых lease. Отдельно состояние паузы, последняя успешная сверка и last successful notification delivery. Idle процесс без задач тоже обновляет heartbeat. |

## Журналы и идентификаторы

Structured JSON на stdout Fastify/Pino, один requestId, сгенерированный edge/API. Удалять произвольный клиентский ID или принимать доверенный заголовок только от edge. Передавать correlationId через DB intent, job, outbox и события провайдера. Запись может включать orderId, paymentAttemptId, jobId, revision, requestId, controller/route template, время UTC, длительность, итог, bounded reason и release digest. Эти ID остаются в ограниченном журнале, labels метрик их не используют.

INFO — старт, штатные терминальные переходы и результаты аудита, WARN — временные проблемы, ERROR — подтверждённый сбой, долгий retry или нарушенный инвариант. DEBUG разрешён на закрытом стенде с синтетическими данными. Даже при исключениях сохранять allowlist полей, исключить body, query, внешние error payload, SMTP текст, raw headers, cookie, OAuth-коды, пароли, API-токены, payment credentials, полный IP/почту и subscription URL. Точные данные аудита доступны ограниченной роли по правилам Identity. [Защита журналов](security.md#данные-сессии-и-журналы)

Ротация по размеру с верхним лимитом Docker logging driver, начально 20 MiB × 5 на контейнер. Операционные события в ограниченном журнале — целевые 14 дней при достаточном диске, по объёму возможна более короткая локальная история. При необходимости расследований выгружать только очищенную выборку в закрытое хранилище. Audit и подтверждённые финансовые записи живут по согласованной политике отдельно. Недоступность log sink не должна блокировать webhook, отказ обязательного Audit append откатывает связанную привилегированную команду.

## Метрики и оповещения

Один локальный Prometheus с ограничением хранения (начально 7 дней и 1 GiB) и Alertmanager для дедупликации и маршрутизации либо существующий сервис с той же функциональностью. Нужны временные окна, гистограммы, сведение инцидентов и повтор оповещений. Метрики API/worker закрыты, агрегаты PostgreSQL доступны через минимальный read-only сбор. Внешний монитор проверяет HTTPS публичного origin и отсутствие periodic heartbeat off-site backup, чтобы замечать потерю VPS. Стартовый scrape 30 с. Метрики имеют ограниченные labels (service, route template, channel, category), без идентификаторов покупателей, заказов, инсталляций из пользовательских данных или payload.

| Сигнал и источник | Начальное предупреждение | Critical и первое действие |
|---|---|---|
| Доступность и HTTP API, duration histogram | 5xx >2% 5 мин при ≥30 запросах или p95 >1 с 10 мин. | Две независимые точки либо 3 внешние проверки подряд, ~2 мин. Проверить TLS/edge/DB, сохранить ingress подтверждений. |
| Webhook и финансы: persist failures, подпись, late/unmatched, backlog, возраст | >1% сбоев записи аутентифицированных событий за 5 мин при ≥20 запросах или просроченная сверка. Ошибки подписи отдельно. | Устойчивый отказ durable ingress 5 мин или нарушение контрольных равенств. Приостановить новые попытки затронутого канала, сохранить durable inbox, открыть сверку с провайдером. |
| Оплачено без выдачи и latency от аллокации до matchedRevision | Любой текущий оплаченный период с PENDING/REVIEW старше 5 мин, группировать по причине, согласованные hold учитывать отдельно. | Возраст >30 мин или более 10 заказов старше 10 мин. Проверить worker, очередь и панель, не повторять начисления. |
| Очередь: oldest ready, depth, retry counters, expired lease | Oldest ready >2 мин или рост 10 мин при ненулевой готовой очереди. | >10 мин при доступной панели или просроченный приоритетный запрет >5 мин. Проверить lease, drift и capacity. |
| Worker heartbeat и checkpoints | Heartbeat старше 60 с, нет прогресса при due. | Старше 2 мин при активной выдаче или после рестарта. Определить причину, убедиться в одном активном писателе и восстановить через verify-first. |
| PostgreSQL и диск: readiness, pool, I/O, WAL | Соединения >80% 5 мин, диск >75% или заметная задержка archive. | DB недоступна 2 мин, диск >90% либо прогноз исчерпания за час. Сохранить БД и журнал, приостановить мутации, освободить безопасные эксплуатационные данные по runbook. |
| Remnawave: probe, 401/403, drift counts и возраст | Три сбоя подряд или неподтверждённые расхождения сверх согласованного окна. | Недоступна >10 мин при оплаченной очереди, подозрение на ключ или необъяснимый массовый drift. Остановить автоматические записи при риске чужих или устаревших изменений. |
| Backup: возраст verified backup, archive lag, last restore proof | Backup просрочен по расписанию, не проверены hash/manifest или WAL lag >5 мин. | Удалённая подтверждённая точка восстановления отстаёт >15 мин либо резервное хранилище недоступно и окно RPO теряется. Поставить релиз на паузу, восстановить архив и проверить диск. |

Группировать по окружению и корню причины. Во время DB outage подавлять зависимые API/worker сообщения, сохраняя счётчик. Window и минимальный объём защищают от единичных выбросов. Critical отправляется дежурному сразу с подтверждением, предупреждения — в рабочий канал со сводкой. Повторы одной причины до изменения состояния ограничены (например, 30 мин Critical, 4 ч WARN). Тишина на обслуживание имеет TTL, владелец и внешний heartbeat остаются. Состояние RESOLVED и проверенный runbook link входят в уведомление. Секреты и клиентские данные исключены.

## Резервное копирование и цели

Проектные цели после стендовой проверки: **RPO ≤15 мин** при непрерывном внешнем архиве WAL, **RTO ≤4 ч** до проверенного открытия коммерческих операций. Доступность отчётов провайдеров и длительность сверки влияют на фактическое RTO. Из одной ночной логической копии возможна потеря изменений почти за сутки, поэтому для цели 15 мин нужен физический backup с PITR. Цели измеряются по последнему подтверждённому удалённому WAL и времени от объявления инцидента до возобновления.

1. Физический full backup по воскресеньям в 01:00 UTC, differential в остальные дни в 01:00 UTC, WAL непрерывно. Выбранный вариант — pgBackRest с S3-совместимым внешним репозиторием, шифрованием клиента и TLS. Инструмент нужен для связного каталога base backups и WAL. Интервал принудительной смены WAL проектно 5 мин, устойчивость контейнера и архива проверить на стенде. Отслеживать подтверждение удалённой записи, непрерывность и задержку WAL до последней точки с изменениями, рост spool. В простое отличать отсутствие изменений от остановки архива по контрольному check и probe. Отдельная ежедневная логическая копия `pg_dump` для выборочного восстановления и проверки переносимости, роли и grants поставляются версионированно. Логический dump запускать в 03:00 UTC после завершения физического задания. При пересечении заданий отложить dump без параллельной борьбы за I/O.
2. Off-site в отдельном аккаунте/сервисе. Хост передаёт резервные копии с ограниченными правами, отдельный субъект обслуживает retention/удаление, на время restore — временное разрешение чтения. Использовать object versioning и отдельно защищённое окно неизменяемости, согласованное с политикой retention репозитория. Планово 5 недель физической истории с соответствующим WAL и 14 дней логических копий. Ключ, с которым работает backup сохранять в защищённом mount. Независимую резервную копию ключа и инвентарь восстановления хранить вне VPS под контролем уполномоченных операторов. Дампы содержат персональные данные.
3. Для каждого задания проверять exit code, опубликованные manifest/checksums, передачу репозитория, непрерывность WAL и целевой таймстамп. Снимок манифеста, deploy digest, schema history, ключи доступа к restore и инструкции доступны после потери VPS. Для выбранной версии pgBackRest проверять `check`, машинный `info` и целостность репозитория `verify`. Отчёт фиксирует ID, timeline, размер, окно времени и результат без содержимого. При использовании spool явно проверить поведение очереди под давлением диска, потеря WAL останавливает допуск по RPO. При ошибке не удалять последнюю подтверждённую цепочку. Мониторинг исключает ложный успех от локального файла.
4. Ежемесячно восстановить выбранную цепочку в изолированной среде, включая PITR между backup. Проверить smoke и финансовую сверку по процедуре ниже. После смены PostgreSQL, инструмента архива, ключа или схемы миграций повторить проверку. Зафиксировать фактическое время RPO/RTO и способность прочитать предыдущие backups.

## Восстановление на отдельном стенде

1. Объявить инцидент и выбрать точку восстановления до повреждения с учётом последнего удалённого WAL. Зафиксировать время, область потерь и ожидаемое окно сверки. Изолировать прежних писателей и подозрительный хост. Сохранить рабочую копию, журналы и поступившие после точки восстановления события в защищённое хранилище при их наличии.
2. На пустом закрытом экземпляре PostgreSQL той же основной версии восстановить физическую копию и WAL до выбранной точки. Для PITR указать время UTC и правильный исходный timeline. Кластер на проверке останавливается на цели с recovery_target_action=pause. Зафиксировать LSN и проверить чтение до перевода в рабочий режим. Для логической копии использовать совместимые schema/data и отдельно роли. Фоновые задачи выключены, внешние записи заблокированы, публичной маршрутизации нет. Стенд читает backup, но не пишет в namespace рабочего архива. Проверить checkpoints, открытие БД, миграции, grants и integrity. Зафиксировать точку и время окончания replay.
3. Проверить пользователей, уникальные identity, статус учётных записей, число заказов, распределённых захватов, движений и периодов по сохранённым контрольным итогам. Проверить связь аллокация ↔ grant, целостность привязок, даты и hold. Для реального восстановления переиздать или массово инвалидировать восстановленные access/refresh/admin sessions и незавершённые OAuth/stage/step-up intents: снимок мог воскресить отозванную сессию. Не включать восстановленные тестовые email и уведомления.
4. Восстановить покрытие платёжного журнала независимым чтением выписки/событий по каждому мерчанту с перекрытием до точки восстановления и до текущего времени. Сохранить внешние ID, replay через стандартный идемпотентный вход сначала в режиме сверки, затем применить подтверждённые факты теми же командами. Сравнить суммы по валютам, аллокации, возвраты и споры. Любая операция после RPO без надёжно связанного заказа уходит в дело, пока не восстановлены снимок и право. Запретить ручной повтор платежа или возврата с неизвестным результатом. До открытия канала проверить, что повтор той же страницы не добавляет новых финансовых записей.
5. Отдельно read-only сверка Remnawave по привязанному ID. Все восстановленные RUNNING и спорные записи перечитать, старые токены lease погасить. При меньшем локальном желаемом сроке или неизвестном ручном DISABLED удерживать запись, пока не восстановлено право. Оплаченный период может быть доказан платёжной и локальной историей. Срок панели служит наблюдением. Повторное применение использует абсолютный профиль и уникальный grant, без сложения срока с датой панели. Проверить хотя бы один ранее оплаченный заказ, повтор replay и случай ожидающей выдачи/возврата. [Инварианты подписок](subscriptions.md#начисление-и-календарь)
6. Зафиксировать результаты и исключения с владельцами. Только после подтверждения целостности и остановки старых писателей перевести восстановленный экземпляр в единственный рабочий режим. Восстановить защиту origin и ingress ACL, открыть read-only API, затем durable ingress и финансовую обработку по проверенным каналам. Выдачу запустить одним worker с verify-first, контролем hold и ограниченным параллелизмом. Новые продажи и возвраты открывать после соответствующей сверки. Проверить dashboard, heartbeat, очередь и резервное копирование нового primary. На учебном стенде применяются sandbox/фикстуры и isolated endpoint, production остаётся изолирован.

## Релиз и откат

**Release checklist.** Манифест образов соответствует прошедшим CI и staging smoke. Подтверждены grants, сетевые границы, TLS, backup/WAL и rollout lock. На стенде проверены миграция, старый runtime на расширенной схеме, контроль финансов, synthetic checkout и тестовое подключение Remnawave. Для релиза есть короткие контрольные окна и наблюдаемые критерии остановки. [CI](testing.md#проверки-ci-и-допуск-релиза)

1. Перед заменой ограничить приём новых платёжных попыток и изменяющих административных команд, если изменение несовместимо. Остановить захват старым worker, дождаться drain. Durable webhook ingress может продолжить при совместимой схеме. При невозможности долговременно принять событие ответить согласно договору адаптера и контролировать повтор и сверку. Успешный ответ допустим только после устойчивого приёма.
2. Применить миграции одним job. Заменить API и статику по digest, worker и финансовые фоновые задачи держать в паузе до smoke. Проверить health/readiness, admin permissions и CORS, оплату в sandbox, worker heartbeat, контрольные равенства, видимость метрик и совместимость панели. Повторить read-only smoke после открытия задач. Smoke на production использует безопасные чтения и выделенные неплатёжные проверки, без реального списания.
3. При rollback снова удержать мутации и прекратить захват, сохранить новые факты и durable intents. Проверить, что старый образ поддерживает текущий schema range, формат событий и состояния созданных после релиза операций. По совместимости переключить статику/API, воркер откатывать только при доказанном отсутствии второго писателя и совместимом lease/инвариантах. Повторить smoke и сверку новых денег и профилей.
4. При необратимом сдвиге сначала сохранить текущее состояние и использовать forward fix. Каталог PostgreSQL, новые платежи и права не откатываются путём наложения старой копии. PITR выполняется на другом экземпляре с последующей сверкой. При внешних эффектах, которые уже нельзя отменить безопасно, оставить соответствующую интеграцию в паузе и возобновить её после reconciliation.

## Реагирование на инциденты

Для Critical дежурный фиксирует время, окружение, релиз, симптомы и затронутые мерчанты/инсталляции. Ограничивает только опасные мутации, сохраняет durable evidence и известные внешние ID, уведомляет ответственного и назначает единый источник решений. Возобновляет запись по критериям из таблицы с проверкой после первого цикла. Ручное исправление денег, сроков или статусов SQL исключено из штатного runbook.

| Инцидент | Ограничение ущерба и возобновление |
|---|---|
| Сайт недоступен | Проверить внешний TLS/сеть, edge, API readiness и DB по порядку. Защитить durable ingress или ответить отказом по договору повторов. После исправления проверить оба origin и состояние событий. |
| Сбой БД или потеря VPS | Остановить новые внешние записи и изолировать второй primary, сохранить артефакты. При деградации проверить storage и архив. При потере восстановить на новом/изолированном экземпляре по runbook с RPO/RTO, финансовой сверкой и проверкой панели. |
| Утечка токена или сессии | Отозвать скомпрометированный доступ, ограничить mutating calls, перевыпустить секреты и проверить результат новым credential. Сохранить redacted следы. [Ротация](security.md#ротация-и-компрометация) |
| Ошибка денег | Приостановить новые платежи/возвраты затронутого канала, сохранять аутентифицированное входящее в durable inbox. Сверить отчёт и неизвестные попытки. Возобновить после финансовых равенств и классификации исключений. |
| Массовая задержка или расхождение панели | Проверить heartbeat, lease, очередь и причину отказа панели. Изолировать запись при нарушении идентичности или версии. Считать подтверждённые оплаты сохранёнными, приоритет — действующие запреты и verify-first. После восстановления ограниченно включить один worker, измерить drift и факт выдачи. |

## Переключение воркера FND-03

1. На изолированной копии выполнить clean и legacy rehearsal FND-02 и тесты процессов. Зафиксировать старый digest, резервную копию, число задач по статусу, номера заказов в RUNNING и их сохранённые цели. Запретить автозапуск старого исполнителя в супервизоре.
2. Остановить все старые процессы API со встроенным worker, включая реплики. Для периода обслуживания старый API можно запустить с `WORKER_ENABLED=false`. Проверить состав процессов и отсутствие незавершённых внешних запросов. Если при остановке результат выдачи неизвестен, приостановить выдачу и сверить спорные заказы и целевые даты с панелью до допуска нового исполнителя.
3. Применить `pnpm --filter @vpn/api db:deploy` ролью миграций. Миграция добавляет таблицу FulfillmentLease и триггер, который отвергает изменения RUNNING от предыдущей версии приложения. Выдать runtime-роли SELECT, INSERT, UPDATE на новую таблицу согласно действующей модели прав. Существующие задания, плановые даты и история остаются на месте. Для унаследованного RUNNING без слота действует прежний порог 5 минут.
4. Запустить новый API и отдельно `pnpm --filter @vpn/api start:worker` из того же собранного релиза. Передать воркеру DATABASE_URL, REMNAWAVE_URL, REMNAWAVE_TOKEN, REMNAWAVE_INTERNAL_SQUAD_UUIDS и применимые параметры панели. На одном сетевом namespace каждому процессу нужен свой WORKER_HEALTH_PORT. По умолчанию probes слушают 127.0.0.1:3002. Проверить GET /health и /ready из этого namespace. API проверяется независимо на /api/ready.
5. Проверить обновление lastHeartbeat, уменьшение числа готовых заданий и освобождение слота завершённого заказа. При потере PostgreSQL цикл опроса остаётся жив, readiness падает после ошибки или устаревания heartbeat. У активной попытки интервал heartbeat равен меньшему из 15 секунд и lease/3. Значения по умолчанию — аренда 90 секунд, HTTP deadline 20 секунд, drain 55 секунд. На SIGINT/SIGTERM readiness падает сразу, новая работа прекращается, активная попытка сохраняет аренду в течение drain. Лимит супервизора должен превышать WORKER_DRAIN_MS. Завершение с кодом 1 по дедлайну требует проверки RUNNING и срока аренды.
6. При росте FAILED проверить attempts, lastError, заказ и сохранённую цель. Исчерпание 15 попыток при временных сбоях или падениях требует оператора. Ошибки авторизации/контракта панели по прежней политике получают длинную паузу. FAILED удерживает последующие заказы этого пользователя. После устранения причины и проверки неизвестного внешнего результата использовать штатный административный requeue.

**Откат.** Остановить новые воркеры и их автоматический перезапуск, дождаться выхода и проверить активные слоты, RUNNING и возможные незавершённые запросы к панели. До разбора расхождений оставить выдачу на паузе. API предыдущего релиза может обслуживать запросы с WORKER_ENABLED=false. Предпочтительный путь восстановления выдачи — исправленный исполнитель с тем же протоколом. Возврат к старому писателю возможен только через отдельно проверенную совместимую миграцию снятия interlock, после сверки и исключения всех новых писателей. Сохранить таблицу поколений, цели и финансовую историю. Восстанавливать production-БД из backup для обычного отката бинарника не требуется.

**Граница COM-04.** PostgreSQL отвергает фиксацию результата, ошибки, повтора или целевой даты прежним владельцем. Уже отправленный HTTP-запрос может дойти после смены аренды. COM-04 должен связать доменную ревизию с verify-first, сверкой фактического состояния и восстановлением актуальной цели. При спорном результате до этой фазы требуется ручная сверка.

## COM-04 · Late writer и расхождения

Новый claim использует текущее назначение и monotonic generation. Перед HTTP проверяются lease, актуальность revision, сроки, источник гранта и удержания. При записи persist intent и бюджет запроса предшествуют отправке. Успех требует read-back и повторного fenced commit. Старые задачи становятся SUPERSEDED при захвате актуальной версии. Потерявшая lease запись увеличивает verification epoch новой задачи, включая уже подтверждённую. Неразобранный случай остаётся видимым для оператора. После падения без сигнала периодическая сверка уже подтверждённых задач обнаруживает позднее расхождение.

Начальные параметры стенда: проверка CONFIRMED каждые 60 секунд, до восьми последовательных попыток и до шести записей на ревизию. У запроса фиксированный deadline. Бюджеты ограничивают исправления дрейфа, до их исчерпания периодические проверки читают панель в той же очереди. Operator endpoint `GET /api/jobs/revision` доступен на закрытом admin listener с `jobs:read`, содержит идентификаторы, ревизию, состояние и безопасный код причины. Для NEEDS_REVIEW сначала проверяют инсталляцию, имя, метку и числовой ID, затем подтверждённое право и все удержания. Нельзя удалять привязку или заменять внешний ID для устранения таймаута. [Матрица](remnawave-integration.md#com-04--матрица-реализации)

Внешний CAS отсутствует. Сходимость наступает после прекращения старых внешних записей и восстановления доступности панели. При ручном управлении одинаковым полем DISABLED источник повторного запрета панели неразличим. Операторы ставят запреты управляемого пользователя через магазин или оставляют его на ручном разборе. Настроить оповещения по возрасту неподтверждённых запретов, NEEDS_REVIEW и просроченному CONFIRMED до допуска production.

## Восстановление доступа персонала

Первый или аварийный ADMIN создаётся с доверенной машины командой pnpm --filter @vpn/api admin:create staff@example.invalid. Использовать выделенный адрес и скрытый ввод пароля. При первом входе подтвердить TOTP, сохранить recovery codes отдельно и завести второго доступного ADMIN.

При потере фактора сотрудник использует одноразовый recovery code либо обращается к ADMIN. Проверить личность по служебному каналу, зарегистрировать recovery case и провести заявку с одобрением другого ADMIN. При единственном ADMIN владелец закрывает ingress, фиксирует инцидент и после проверки личности выполняет pnpm --filter @vpn/api admin:reset-2fa staff@example.invalid INC-123 из привилегированной консоли. Проверить отзыв сессий, привязать новый фактор, сохранить recovery codes и вернуть доступ через ограниченный ingress.

## Разбор возврата и выдачи

- Из заказа открыть подтверждённое CAPTURE, историю возвратов и распределение. Сверить валюту, сумму, действующие резервы и доказательства. Зарезервировать с причиной. Одобрение другого ADMIN сохраняет резерв в ожидании провайдера. Повтор после обрыва использует исходный Idempotency-Key.
- Для актуальной выдачи использовать повторную проверку. Истёкшая revision требует открыть текущую подписку. При неизвестной принадлежности профиля сохранить ограничение и зафиксировать решение. Desired и observed читаются отдельно.
