# VPNShop V2 · Development Rules

- Continue existing code, data and deployment contracts. Reuse the PostgreSQL roles and transactional invariants, ledger, durable jobs, security guards, RBAC and audit. Use the least invasive change that fulfills the active pass. Store no production material in test fixtures.
- Work in `work/vpnshop-v2` from current `main` or safely continue its existing commits. Preserve unrelated changes. Merge, production changes, live payments/refunds, writes to live Remnawave and destructive legacy migration require separate authorization.
- Require tests, lint, typecheck and appropriate security evidence for each pass. Record both completed and unavailable checks. Use scoped local review in each pass. The independent full audit belongs to PASS 07.
- Mount role-specific secrets with mode 0400 inside a 0700 directory. Check effective ownership with Docker namespaces. Never write credentials, private links or unredacted provider data to code, logs, diagnostics or artifacts. Keep existing no-new-privileges, nonroot execution, read-only mounts, trust boundaries, mTLS verification and HTTP allowlists. Use isolated synthetic fixtures and keep infrastructure release blockers visible.
- Preserve MZT Premium Balance. Reuse the existing logo, SVG labyrinth, graphite dark palette, restrained violet accents and text hierarchy, fonts, chamfered geometry, icons, sidebar and responsive navigation. Build new UI from established tokens and primitives. Avoid default admin templates, unrelated palettes, gratuitous gradients and effects. Infrastructure passes preserve application layout.
- Keep the Master Specification and Implementation Plan current. Update the corresponding domain documentation when changing verified behavior. Record external prerequisites and staging results separately. See [Master Specification](V2_MASTER_SPEC.md), [Implementation Plan](V2_IMPLEMENTATION_PLAN.md), and [Design Contract](design/MZT-PREMIUM-BALANCE.md).
