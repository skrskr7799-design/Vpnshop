# Административная панель VPNShop

Актуальные права OWNER, управление сотрудниками, ручная активация и переход на username описаны в [VPNShop V2 Administration](V2_ADMINISTRATION.md). Общий протокол команд и ограничения финансовых операций ниже продолжают действовать.

Phase 4. Админка читает операторские проекции и вызывает команды модулей через закрытый Admin API. React-приложение обращается только к своему API. Ключи платёжных систем, Remnawave, Prisma и строки подключения доступны только backend. [Границы модулей](architecture.md#владение-данными-и-разрешённые-зависимости) · [Identity](identity.md)

## Разрешения

Сервер разрешает каждую пару «тип сессии + permission + объект» по актуальной роли. Ответ строится по allowlist полей. Проверки выполняются до чтения детали/записи, а чувствительная команда сверяет статус и полномочия повторно в транзакции. Admin API на отдельном origin с host-only SameSite=Strict cookie, TLS, CIDR на входе, exact Origin на небезопасных методах. Заголовки доверенного прокси принимаются только от известных прокси; продакшен-проверка подтверждает фактический IP. Публичный JWT для админки бесполезен. UI использует /me для видимости кнопок, решение принимает backend. [Текущий gate](../apps/api/src/modules/admin/admin.middleware.ts) · [Identity](identity.md)

### Протокол чувствительной команды

1. Клиент показывает объект, версию, изменение или сумму и запрашивает причину `reason` (5–500 символов). Тело команды также содержит `expectedVersion` (версия агрегата или эквивалентный CAS) и `confirmationId` из step-up. Сервер проверяет подтверждение, связанное с sessionId, permission, объектом и хешем нормализованной команды с причиной. Истечение или несовпадение → 403 STEP_UP_REQUIRED. [Шаг подтверждения](identity.md#административная-аутентификация)
2. `Idempotency-Key` по общим правилам C3 со scope из actorId, команды и цели. Принимается с тем же телом и действующим разрешением. Точное повторное чтение результата возможно после расходования подтверждения, если совпали ключ, actor, команда и тело. Для новой операции одноразовая запись расходуется атомарно с эффектом. Конфликт тела → 409 IDEMPOTENCY_CONFLICT, конфликт версии → 409 VERSION_CONFLICT. Ошибка аудита откатывает локальную мутацию. [Формат ключа](user-account.md#общие-правила-http)
3. Audit append рядом с бизнес-записью/outbox. Сохранять actorId, роль, объект, разрешение, краткую причину, commandId, requestId, correlationId, время, безопасную дельту и результат. Отдельные события intent и окончательного результата внешней команды используют один correlationId. Входы и отказ чувствительного действия журналируются отдельно с безопасной причиной. Финансовые и внешние подтверждения пишут команды владельца модуля, с источником подтверждения. Ошибки оператора исключают токены, заголовки и данные конфигураций. [Audit](architecture.md#владение-данными-и-разрешённые-зависимости)

## Операционный Dashboard

Все запросы A1 возвращают `asOf`. Каждый блок источника содержит `{observedAt,state,reasonCode,data}`. Состояния — FRESH, STALE, UNAVAILABLE. При отсутствии прошлого наблюдения значения observedAt и data равны null. Периоды полуоткрытые в UTC, явные `from,to` и начальное окно 30 дней с лимитом 366 дней. Фоновый heartbeat и проба metadata живут по таймеру сервиса. Polling в браузере только на видимой вкладке. При выпадении источника сохраняется последняя успешная метрика с отметкой свежести. Проверять запросы на копии данных и вводить отдельную агрегатную проекцию при измеримой нагрузке.

|---|---|---|---|

## Контракты закрытого API

Все пути ниже на admin origin с префиксом `/api`. Чтения без тела. Типы `ID`, время, деньги, `Page<T>`, limit/cursor и базовые ошибки совпадают с кабинетом. Списки используют cursor (createdAt/id или другой объявленный стабильный индекс) и допустимые фильтры. Legacy page/pageSize для уже существующих маршрутов можно поддержать на переходе как отдельный формат без смешивания двух типов пагинации. Поиск exact по ID/reference/проверенному email; email передавать через несохраняемую форму и исключить query из логов/трассировки. Новый эндпоинт поиска для чувствительных полей использует POST без бизнес-эффекта. Команды по умолчанию выдают 202 `{commandId, status, targetId}` и сохраняют intent, 201 для созданных сущностей, 200 для синхронного изменения. `GET /api/commands/:id` возвращает `{commandId,status,targetId,reasonCode,updatedAt}` с правом исходной операции и доступом к её цели. Без тела, чужой или отсутствующий ID даёт 404, допустимые статусы ACCEPTED, RUNNING, WAITING_EXTERNAL, SUCCEEDED, FAILED, NEEDS_REVIEW. Интеграционный тест проверяет, что отозванная роль теряет чтение статуса команды, а UNKNOWN внешнего провайдера остаётся WAITING_EXTERNAL либо NEEDS_REVIEW. При polling клиент ждёт известного результата. [HTTP-правила](user-account.md#общие-правила-http)

## Фактический протокол клиента

- POST /api/auth/step-up принимает operation, permission, targetId, expectedVersion, reason, command, password и code. Подтверждение действует 5 минут. POST /api/commands/:operation/:target или именованный маршрут принимает expectedVersion, reason, command, confirmationId и Idempotency-Key. Версия плана и персонала — целое число. Для заказа, клиентского статуса и поддержки используется ISO timestamp. Выдача и компенсация используют ревизию подписки. Локальная транзакция возвращает HTTP 200 с commandId, status, targetId и result.
- Старые PUT/PATCH/DELETE тарифов и replay legacy job заменены версиями команд. Публикация меняет условия для последующих покупок. Снятие сохраняет историю. Отложенное начало и окончание продаж, трафик и выбор squads на уровне оффера остаются в целевом контракте. Профиль COM-04 использует конфигурацию установки.
- A7 показывает движения по заказу. /api/payments/transactions?unallocated=true показывает незачтённые CAPTURE. Оператор разбирает дела, созданные вручную. Закрытие блокирующего дела провайдера требует доказательства за пределами этого маршрута.
- Неподтверждённый резерв действует 24 часа. Другой ADMIN подтверждает неизменяемую сумму. Одобренный резерв остаётся в APPROVED_WAITING_PROVIDER. При проверке суммы учитываются имеющиеся резервы и подтверждённые reversal facts под блокировкой денежного контура мерчанта.
- Повтор выдачи ставит актуальное назначение в VERIFY_PENDING. KEEP_HOLD фиксирует решение при конфликте идентичности. Новая привязка требует проверенного источника доказательства.
- A9 добавляет независимый интервал, уникальный по инциденту в подписке. Владелец утверждает B2 до включения ADMIN_COMPENSATION_POLICY=incident-append-v1. История покупок, деньги и прежние интервалы сохраняются.
