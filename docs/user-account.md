## Общие правила HTTP

ID — непрозрачная строка 1–128 символов из контролируемого формата модуля. Времена — ISO 8601 UTC, суммы — целые minor units с валютой, допустимые значения из Pricing и Payments. Ввод строгий, неизвестные поля отклоняются. `Page<T> = {items:T[], nextCursor:string|null}`. В списках `limit` от 1 до 100, по умолчанию 25, cursor непрозрачен и связан с сортировкой, текущим владельцем и фильтрами. Сортировка стабильна по времени и ID. Ошибки сохраняют `{error:{code,issues?}}`, безопасные `requestId` и детали могут добавляться как общие поля. Базовые ошибки — 400 VALIDATION_ERROR, 401 UNAUTHENTICATED, 403 BAD_ORIGIN или ACCOUNT_BLOCKED, 404 NOT_FOUND, 429 RATE_LIMITED, 503 TEMPORARILY_UNAVAILABLE. Приватные ответы no-store. Каждая операция с объектом повторно проверяет ownership на сервере. [Обработчик ошибок](../apps/api/src/lib/error-handler.ts) · [Session-контракт](identity.md)

Для C3, C7, C9 и C11 обязателен `Idempotency-Key` (UUID или случайная строка 16–128 ASCII). Область — пользователь, команда и целевой ресурс. Сервер сохраняет хеш нормализованного тела и устойчивый результат/ID. Совпавший повтор возвращает тот же объект, конфликт тела даёт 409 IDEMPOTENCY_CONFLICT. Клиент меняет ключ только при явно новом действии. Повторная отправка после обновления сессии допустима с прежним ключом и подтверждённой принадлежностью. Команды исходят из same-origin; для состояния используются проверка Origin и сессионные cookies. [Транзакции](architecture.md#точки-входа-и-транзакции)

## Контракты кабинета

`Offer` содержит `{id,planId,name,version,durationMonths,price:{amountMinor,currency},deviceLimit,trafficLimitBytes,trafficStrategy,availableUntil}`. `Snapshot` содержит те же коммерческие условия на момент появления заказа, включая версию и название, `policyVersion,snapshottedAt,expiresAt` и зафиксированные дополнительные ограничения. Публичный снимок исключает внутренние ID групп. `MoneyStatus` отдельно от `DeliveryStatus`. Первый хранит проекцию `{orderState,allocationState,refundState,reviewRequired}`. Order state — OPEN, ALLOCATED, EXPIRED или CANCELED по Phase 2. Allocation state — NONE или ALLOCATED. Refund state — NONE, PENDING, PARTIAL или FULL по зачтённому capture, подтверждённый частичный возврат не скрывается при появлении нового запроса. `reviewRequired` учитывает спор, излишек или невыясненный результат независимо от зачёта. Delivery status выводится из права, назначения и наблюдения. `Attempt` содержит `{id,channel,status,createdAt,updatedAt,expiresAt,reasonCode}` с nullable полями отсутствующих данных. Статусы попыток и назначения берутся из фаз 2–3. Формат UI ниже не меняет доменные состояния. [Платёжные состояния](payments.md#жизненный-цикл-и-отказы) · [Состояния подписки](subscriptions.md#состояния-и-корректировки)

### Реализованный контракт ACC-02 и ACC-03

- Текущие формы ответа определяют [shared DTO](../packages/shared/src/schemas/account.ts) и [проекции API](../apps/api/src/modules/account/projections.ts). C1 использует `EMPTY / ACTIVE / SCHEDULED / EXPIRED / HELD / LEGACY_REVIEW` для права и `NOT_REQUESTED / WAITING / READY / SCHEDULED / EXPIRED / HELD / REVIEW` для выдачи. READY требует совпадения текущего периода, ревизии и свежего подтверждения от подключённой панели.
- C5 возвращает `orderStatus`, `orderState`, `moneyStatus`, `deliveryStatus` и `periodId`, включая отдельные `UNKNOWN`, `LATE_CAPTURE` и `CAPTURE_RECORDED`. Списки C2 history, C5 и C6 принимают `cursor/limit`. Дальнейшие фильтры C5 и дополнительные измерения статуса возврата остаются целевой спецификацией.
- C4 повторяет проверку периода, удержаний, фактического профиля и текущей family после HTTP. Режим без подключённой панели возвращает `PANEL_UNAVAILABLE`. Клиент получает секрет только по кнопке и держит ссылку/QR в памяти карточки до закрытия, потери права или истечения 60 с. Диагностика денежного состояния и заказа секрет не содержит.
- C8–C11 используют `SupportCase`, `SupportMessage` и `SupportEvent`. C10 возвращает пагинированные сообщения и `history` с публичными статусами. `cursor` и `historyCursor` независимы. Привязку дела к заказу владельца дополнительно гарантирует составной FK; C9/C11 атомарно проверяют ключ команды. Сетевые повторы в открытой форме используют тот же ключ. [Операции поддержки](admin.md#контракты-закрытого-api)
- Тарифы используют существующий C3 в кабинете, присваивающий 30-минутное окно. C7 остаётся закрытым для обычной работы до допуска Platega. Интерфейс объясняет недоступность канала; реальные платежи и выдача остаются закрыты при выключенной конфигурации интеграций.

## Отображение права и реализация frontend

* Полуоткрытые интервалы, календарные месяцы UTC и начисление при зачёте применяются по Phase 2. Интерфейс форматирует даты в часовом поясе пользователя с отметкой зоны. Отсчёт строится по `serverTime` и абсолютной границе, на границе перечитывается сервер. Продление с новой ценой или лимитом меняет будущий период по согласованному правилу. Задержка панели создаёт статус и, при соблюдении утверждённого SLA, одно решение о компенсации по incidentId. [Правила времени](subscriptions.md#начисление-и-календарь)
* Оставить React Router и TanStack Query в web. `AccountLayout` с вложенными маршрутами и функциями subscription, orders, security, support. Query keys из ресурса, фильтров и области текущего principal, стандартное обновление по событию, видимости вкладки и короткий polling только для ожидающих заказа/выдачи. После состояния терминала или ухода со страницы polling прекращается. При смене principal отменять in-flight, чистить кэш, закрывать QR и синхронизировать выход между вкладками.
* Общие типы и Zod-схемы для ввода, ошибок и стабильных ответов вынести в `@vpn/shared`. Формы проверяют ввод локально, затем сервером отображаются field issues. Для списков хранить несекретные фильтры и cursor в URL, поиск персональными данными не сохранять в телеметрии. Повторно использовать Field, Button, Alert и PageStatus. Общие примитивы доступа и токены интерфейса подготовить для будущей дизайн-системы.
* Для секрета использовать отдельный вызов fetch с no-store без записи ответа в React Query. Хранить URL только в памяти открытой карточки и очистить при навигации/logout. QR формируется локально, его реализацию выбрать при кодировании по измеримой необходимости. Клиент не загружает присланный URL для автоматической «диагностики». [Требования Phase 3](remnawave-integration.md#получение-конфигурации-владельцем)
* Приёмка UI включает мокированные состояния таблицы экранов, проверку контракта Zod, сценарий двух реальных сессий для BOLA, смену пользователя во время запроса, повтор POST после потери ответа, навигацию клавиатурой, управление фокусом и проверку сети/кэшей при показе ссылки. Оплата проверяется на изолированном стенде с принятым адаптером, подключение повторяется с тестовым узлом Phase 3.

**Разрешение расхождения фаз.** В обзоре Phase 2 ссылка была `GET /api/me/subscription/link`. Phase 3 описывает `POST /api/me/subscription/access` с явным действием, проверкой Origin/CSRF и запретом кеширования. Phase 4 принимает маршрут Phase 3 как единственный контракт раскрытия, `GET /api/me/subscription` остаётся проекцией статуса. ## Клиентский интерфейс UX-02

- После входа обзор показывает действующее право, срок и статус подключения. CTA ведёт к подключению, деталям заказа или поддержке в зависимости от состояния.
- Каталог открывает подтверждение условий. Повтор сохраняет ключ конкретного оффера. OFFER_CHANGED закрывает устаревший выбор и обновляет каталог. Каналы оплаты показывает текущий заказ по данным API.
- На подписке отдельно видны право, границы периодов и наблюдение панели. Устаревший профиль скрывает действие подключения. Ссылка выдаётся через C4 и живёт в компоненте до закрытия, смены экрана или периода, logout либо таймера. QR строится локально.
- Меню на телефоне открывается в native drawer. После отзыва устройства или смены способа входа интерфейс показывает подтверждённый результат. Reauth остаётся частью управления способами входа. [Маршруты](../apps/web/src/App.tsx) · [Дизайн](frontend.md)
